## ۱) باگ گزارش‌شده: `table Customer has no column named isWalkIn`

### ریشه

«صفر کردن» بعد از خالی کردن جدول‌ها، «مشتری گذری» را دوباره می‌سازد. کدِ سازنده
ستون `isWalkIn` را داخل `INSERT` می‌نوشت، **بدون اینکه بپرسد این ستون هست یا نه**.
ستون `isWalkIn` در نسخه‌های بعدی به `Customer` اضافه شده (از `UPGRADES`)، ولی در
دیتابیس‌های قدیمیِ نصب‌شده وجود ندارد.

نتیجه: ترتیب کارها این بود که **اول** داده پاک می‌شد و **بعد** با خطای SQL
متوقف می‌شد. یعنی بدترین حالت ممکن: نه داده، نه کاربر مدیر، و پیام فقط یک خطای
انگلیسی SQLite.

### طرح اصلاح (سه لایه، هر سه لازم)

1. **پیش‌بررسی اجباری** (`preflight`) در سه مسیر — ابزار آفلاین
   (`tools/reset-ui/reset-core.mjs`)، مسیر آنلاین (`apps/api/src/common/reset.ts`)
   و صفحه‌ی ابزار: اگر جدول/ستون لازم نیست، **قبل از هر تغییری** با پیام فارسی
   متوقف می‌شود.
2. **`INSERT` بر اساس ستون‌های واقعی**: `PRAGMA table_info("Customer")` خوانده
   می‌شود و فقط ستون‌های موجود در `INSERT` می‌آیند.
3. **برگردانی خودکار**: اگر با این حال وسط کار خطایی رخ داد، پشتیبانِ همان لحظه
   برگردانده می‌شود (در دور ۳۰ این محافظ به مسیر **آنلاین** هم اضافه شد — پایین).

### دلیل اعتماد

```
node scripts/ui-check/reset-tool.test.mjs      → 92 ✔ / 0 ✘
node apps/api/test/reset.test.js               → 37 ✔ / 0 ✘
node apps/api/test/recovery.test.js            → 50 ✔ / 0 ✘
```

سه ردیف `recovery.test.js` مستقیماً همین مشکل را می‌سازند: دیتابیس قدیمی
**بدون** ستون `isWalkIn` → صفر کردن موفق می‌شود؛ خطای وسط کار → «موفق» گزارش
نمی‌شود؛ دیتابیس بعد از تلاش ناموفق سالم است.

## ۳) دور ۳۰ — بازرسی ابزارها

### ۳-۱) `POST /api/renew-parse` بدون محافظ CSRF/مبدأ

**ریشه:** هر مسیر POST در `tools/license/server.mjs` اول `guardMutation(req)` را
صدا می‌زد — جز یکی. یعنی هر صفحه‌ای که در مرورگر کاربر باز باشد می‌توانست
(با `fetch` ساده) بدنه‌ی یک لایسنس را به ابزار بفرستد و پاسخ تحلیل را بخواند.
**اصلاح:** همان `guardMutation`. **تست:** `license-guard.test.mjs` حالا تعداد
مسیرهای POST را با تعداد `guardMutation` می‌سنجد و ترتیب را هم: محافظ باید
**قبل** از خواندن بدنه بیاید — ۶۸ ✔.

### ۳-۲) بدنه‌ی بزرگ: اتصال معلق یا `ECONNRESET`

**ریشه:** `readBody` وقتی از سقف حجم می‌گذشت `reject` می‌کرد ولی پرامیس را
`settle` نمی‌کرد؛ در نسخه‌ی لایسنس بدتر: `req.destroy()` سوکت را می‌کشت، پس
مرورگر `ECONNRESET` می‌دید و **پیام فارسی ۴۰۰ هرگز نمی‌رسید**.
**اصلاح:** پرچم `settled` + شنونده‌ی `aborted` + `req.pause()` به‌جای
`destroy()` در **هر دو** سرور. **اثبات زنده:**

```
بدنه‌ی ۴۰۰ کیلوبایتی → {"ok":false,"message":"بدنه‌ی درخواست بیش از حد بزرگ است."}
JSON خراب            → {"ok":false,"message":"JSON نامعتبر."}
renew-parse بی‌توکن  → ۴۰۰ «توکن امنیتی نامعتبر است»
issue / file / download / keygen → ۲۰۰
```

### ۳-۳) پورت اشغال: استک‌تریس انگلیسی و بسته شدن پنجره

**ریشه:** هیچ شنونده‌ی `error` روی سرور نبود؛ `EADDRINUSE` به‌شکل
`node:events:497 throw er` ریخته می‌شد و پنجره‌ی کنسول بسته می‌شد.
**اصلاح:** شنونده‌ی `error` در هر دو سرور با پیام فارسی و راه‌حل:
«پورت در حال استفاده است؛ ابزار از قبل باز است → همان صفحه را استفاده کنید،
یا `FD_LICENSE_UI_PORT=4322`». **اثبات:** با گرفتن مصنوعی پورت ۴۴۱۵ همین پیام
چاپ شد و پروسه با کد ۱ خارج شد (نه استک‌تریس).

### ۳-۴) مرورگر **قبل** از بالا آمدن سرور باز می‌شد

**ریشه:** این باگ در ابزار «صفر کردن» رفع شده بود ولی `tools/license/start.cmd`
هنوز `start "" "http://127.0.0.1:%PORT%/"` را **قبل** از اجرای `node` صدا می‌زد
⇒ صفحه‌ی `ERR_CONNECTION_REFUSED` در اولین اجرا.
**اصلاح:** الگوی درست در هر دو `start.cmd` و هر دو `start.sh`. در شل، به‌جای
`sleep` ثابت (که روی کمپیوتر کند کافی نیست و روی سریع بی‌دلیل کند است)، **صبر
تا واقعاً جواب دادن سرور** (`curl -sf` یا `/dev/tcp`، حداکثر ۱۵ ثانیه).
**تست:** `print-quality.test.mjs` حالا **هر دو** ابزار را می‌سنجد — ۳۷ ✔.

### ۳-۵) CLI صفر کردن روی کمپیوتر بی‌داده، پیام گمراه‌کننده

**ریشه:** CLI اول چاپ می‌کرد «۰ ردیف داده پاک می‌شود؛ یک پشتیبان خودکار گرفته
می‌شود» و **بعد** خطای «فایل دیتابیس پیدا نشد» می‌داد. کاربر می‌ماند که آیا
پشتیبانی گرفته شده و داده‌اش کجاست.
**اصلاح:** بررسی `inv.exists` **قبل** از گزارش، با مسیر بررسی‌شده و راهنما
(`FD_DATA_DIR` / `FD_DB_FILE`). **اثبات:** روی پوشه‌ی خالی:
`ℹ فایل دیتابیس نیست — چیزی برای صفر کردن وجود ندارد.` با کد خروج ۱.

### ۳-۶) صفر کردن **آنلاین** برگشت خودکار نداشت (مهم‌ترین مورد دور ۳۰)

**ریشه:** از دور ۲۸ ابزار آفلاین در خطا دیتابیس را از پشتیبان برمی‌گرداند، ولی
مسیر `POST /system/reset` (وقتی برنامه باز است و ابزار از راه API صفر می‌کند)
این محافظ را نداشت: خطا وسط `DELETE`ها ⇒ دیتابیس نیمه‌کاره، نه داده، نه مدیر.
**اصلاح:** بلوک محافظ دور همه‌ی تغییرات؛ در خطا:
۱) `resetDb()` (بستن اتصال libSQL — وگرنه صفحه‌های کهنه و WAL بازگردانی را
بی‌اثر می‌کند)، ۲) کپی پشتیبان روی فایل، ۳) پاک‌کردن `-wal`/`-shm` کهنه.
خطا هم دیگر فقط `message` برنمی‌گرداند: `rolledBack` و `backupFile` هم می‌آیند.
**اثبات (تست واقعی، نه ادعا):** در `reset.test.js` یک تریگر
`BEFORE DELETE ON "Sale"` روی فایل دیتابیس ساخته می‌شود، بعد صفر کردن:

```
✔ صفر کردن شکست خورد (نه ۲۰۰ بی‌اثر)
✔ پیام می‌گوید برگردانده شد
✔ پرچم rolledBack در پاسخ هست
✔ داده‌ها بعد از شکست سر جایشان‌اند   (۳ فروش قبل = ۳ فروش بعد)
✔ برنامه بعد از برگشت هنوز کار می‌کند (ورود مدیر)
```

### ۳-۷) ابزار صفر کردن، نتیجه‌ی خطای مسیر API را دور می‌ریخت

**ریشه:** `resetThroughApi` در `tools/reset-ui/server.mjs` در خطا فقط
`{ok:false, message}` می‌ساخت و `rolledBack` را می‌انداخت؛ صفحه‌ی ابزار
(`ui.html`) شرط `r.rolledBack` دارد و هرگز آن را نمی‌دید.
**اصلاح:** کل بدنه‌ی خطا پاس داده می‌شود.

## ۶) چیزهایی که روی این سیستم **قابل سنجش نبود** (صادقانه)

1. **ویندوز/`.cmd`**: این محیط لینوکس است. منطق `start.cmd` بازخوانی و
   بررسی رشته‌ای شد (`timeout /t` قبل از `start`، بدون کوتیشن تودرتو)، ولی
   **اجرا نشد**. اولین اجرای واقعی روی ویندوز باید دیده شود.
2. **`cargo`/NSIS/Tauri**: Rust در این محیط نیست. `npm run doctor` تنها مورد
   ناکام را همین می‌داند («Rust نصب نیست»). ساخت نصب‌کننده و آزمایش بسته‌ی
   واقعی روی ویندوز انجام می‌شود (`npm run desktop:build` سپس `npm run test:packaged`).
3. **برگردانی پشتیبان روی ویندوز**: در لینوکس `copyFileSync` روی فایل باز
   کار می‌کند؛ روی ویندوز `EBUSY` می‌دهد. برای همین در هر دو مسیر **اول**
   اتصال بسته می‌شود (`resetDb()` / `db.close()`)، بعد فایل عوض می‌شود. این
   ترتیب در کد و در تست هست، ولی سختیِ واقعی فایل‌سیستم ویندوز این‌جا دیده نشد.
4. **اندازه‌گیری کارایی روی کمپیوتر مشتری**: اعداد کارایی (مثل
   `/reports/cashbook` یک سال ≈ ۱۳۵ms / ۱۷۲۵KB) روی این ماشین با ۱۵هزار فروش
   اندازه‌گیری شده؛ روی لپ‌تاپ ضعیف‌تر عدد بزرگ‌تر است. کاهش اصلی (صفحه‌بندی و
   حذف رندر بی‌کران) به سخت‌افزار وابسته نیست.
