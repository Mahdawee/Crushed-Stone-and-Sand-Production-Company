# دور ۳۶ — اجراکننده‌های ابزارها، و شکست واقعی ساخت نصب‌کننده

تاریخ: ۲۰۲۶/۱۱/۱۰ · نسخه: 0.1.0 · شاخه: `arena/5ac72d50-crushed-stone-and-sand-product`

دو گزارش کاربر در این دور:

> «اجراکننده‌های ابزارهای لایسنس و ریست‌کننده به درستی کار نمی‌کند و باز
> نمی‌کنند ابزارها را…»

و خروجی `npm run desktop:build` روی ویندوز:

```
glob pattern tools/reset-ui/**/* path not found or didn't match any files.
failed to build app: failed to build app
```

**۵ باگ** پیدا و رفع شد. دو موردشان «برنامه اصلاً کار نمی‌کند» بودند و
هر دو **از تغییرات دور ۳۵ من** می‌آمدند.

---

## باگ ۱ — `tools/reset-ui/**/*` هیچ فایلی پیدا نمی‌کرد (ساخت می‌شکست)

**ریشه:** الگوهای `bundle.resources` نسبت به پوشه‌ی **`src-tauri/`** حل
می‌شوند، نه ریشه‌ی مخزن. دور ۳۵ الگو را از `tools/**/*` به
`tools/reset-ui/**/*` تغییر داد — و هر دو، زیر `src-tauri/` وجود ندارند.
دور ۳۴ با `tools/**/*` هم شکسته بود؛ فقط کسی تا امروز بیلد نگرفته بود.

**چرا تست‌ها نگرفتند:** بررسی با `String(r).startsWith('tools/')` نوشته
شده بود؛ یک مقایسه‌ی **متنی**. الگو در متن درست به‌نظر می‌رسید، ولی در
واقعیت هیچ فایلی نمی‌گرفت.

**اصلاح:**
* `scripts/build-desktop.mjs` تابع `stageTools()` گرفت: قبل از `tauri build`،
  ابزارها را از `tools/<نام>` به `src-tauri/tools/<نام>` کاپی می‌کند و
  `src-tauri/tools` را از نو می‌سازد (بدون باقی‌مانده‌ی قدیمی).
* فهرست کاپی صریح است: `BUNDLED_TOOLS = ['reset-ui']` — **ابزار لایسنس
  عمداً کاپی نمی‌شود** (دور ۳۵).
* خودِ `stageTools()` الگوها را با `fs.globSync` حل می‌کند و اگر الگویی خالی
  بود، بیلد را **قبل از** رسیدن به Tauri با پیام فارسی می‌ایستد.
* `src-tauri/tools/` در `.gitignore` رفت (خروجی ساخت است، نه منبع).

**چرا این راه و نه `../tools/**/*`:** مسیر بیرون از پوشه‌ی برنامه به رفتار
نسخه‌ی Tauri وابسته است و ماشین من ویندوز/Tauri ندارد که تأییدش کند. کاپی
کردن قطعی است و روی هر نسخه‌ای کار می‌کند.

**اعتماد:** شبیه‌سازی مرحله‌ی Tauri روی همین ماشین:

```
OK  api/**/*        -> 4379 files
OK  tools/**/*      ->    8 files
OK  public-key/**/* ->    1 files
✅ هیچ الگوی خالی و هیچ ابزار لایسنسی در بسته نیست
```

## باگ ۲ — `start.cmd`ها با پایان‌خط LF در مخزن بودند

**ریشه:** `tools/*/start.cmd` با LF ذخیره شده بودند. cmd.exe با فایل LF
همیشه درست کار نمی‌کند: `goto`/`:label`، بلاک‌های پرانتزی و `^` در انتهای
خط می‌توانند بشکنند. نشانه‌اش «پنجره باز می‌شود و فوراً بسته می‌شود» است.

**اصلاح:** `.gitattributes` اضافه شد (`*.cmd text eol=crlf`) و هر دو فایل با
CRLF ذخیره شدند. تست جدید هم CRLF بودن و «هیچ LF تنها» را بررسی می‌کند.

## باگ ۳ — باز کردن مرورگر می‌توانست کل سرور را بکشد

این جدی‌ترین باگ «باز نمی‌شود» بود:

```
Error: spawn xdg-open ENOENT
  errno: -2, code: 'ENOENT', syscall: 'spawn xdg-open'
node:events:497  throw er; // Unhandled 'error' event
```

`spawn` وقتی اجراپذیر نبود، خطای **غیرهمگام** می‌دهد؛ `try/catch` آن را
نمی‌گرفت و Node کل پروسه را می‌بست. یعنی «مرورگر باز نشد» به «ابزار کلاً
بالا نیامد» تبدیل می‌شد — و روی ویندوز/لینوکسِ بدون `xdg-open` تکرارشدنی بود.
اصلاح: هر فرزندِ باز‌کننده‌ی مرورگر `on('error')` دارد (در
`tools/shared/tool-server.mjs`).

## باگ ۴ — پورت اشغال یعنی «ابزار باز نمی‌شود»

**ریشه:** اگر پورت ۴۳۲۱/۴۳۲۲ اشغال بود، سرور با `EADDRINUSE` می‌مرد. و
رایج‌ترین حالت: کاربر قبلاً ابزار را باز کرده و پنجره‌اش را نبسته.

**اصلاح:** تابع مشترک `listenWithFallback` (در `tools/shared/`):
* اگر روی پورت مشغول **همین ابزار** است (`GET /__tool` شناسه می‌دهد)،
  نسخه‌ی دوم ساخته نمی‌شود؛ همان صفحه باز می‌شود.
* اگر پورت اشغال است ولی ابزار ما نیست، تا ۲۰ پورت بعدی امتحان می‌شود.
* سرور فقط وقتی می‌میرد که هیچ پورتی آزاد نباشد — با پیام فارسی.

## باگ ۵ — مرورگر با تأخیر حدسی باز می‌شد؛ گاهی دو بار

**ریشه:** `start.cmd` بعد از `timeout /t 2` مرورگر را باز می‌کرد و
`start.sh` هم جداگانه با curl صبر می‌کرد. روی کمپیوتر کند، سرور آماده نبود →
ERR_CONNECTION_REFUSED. و اگر پورت اشغال بود، مرورگر صفحه‌ی ابزار **دیگری**
را نشان می‌داد.

**اصلاح:** مرورگر حالا **در خود سرور و دقیقاً بعد از `listening`** باز
می‌شود (`openBrowser`). اجراکننده‌ها فقط `server.mjs` را صدا می‌زنند؛ هیچ
تأخیر ثابت و هیچ `start` تودرتو در cmd نمانده است. `FD_NO_BROWSER=1` برای
تست/CI.

## باگ ۶ (فرعی) — مسیر داده‌ی «ساختگی» در نسخه‌ی نصب‌شده

`data-dir.mjs` گزینه‌ی `repo` را از `root/../..` می‌ساخت. در نسخه‌ی نصب‌شده
این می‌شد `<نصب>\_up_\data` — مسیری که هیچ‌وقت دیتابیس ندارد. حالا فقط وقتی
افزوده می‌شود که `data/farday.db` یا پوشه‌ی `tools/` کنارش باشد (نشانه‌ی
ریشه‌ی مخزن واقعی).

## تست جدید: `scripts/ui-check/tool-runners.test.mjs`

تست‌های قبلی فقط **متن** فایل‌ها را می‌خواندند (`/start ""/.test(cmd)`)، پس
باگی که در رفتار بود دیده نمی‌شد. این سوئیت ابزارها را واقعاً اجرا می‌کند:

| بررسی | چه چیزی را می‌گیرد |
|---|---|
| سرور بالا می‌آید و `/` و `/__tool` جواب می‌دهند | شکست راه‌اندازی |
| پورت اشغال → پورت بعدی، پیام فارسی | مرگ با EADDRINUSE |
| نسخه‌ی دوم روی همان پورت → بازاستفاده | نسخه‌های تکراری |
| مرورگرِ ناموجود → سرور زنده می‌ماند | باگ `Unhandled 'error' event` |
| `--port` برای هر دو ابزار | پورت ثابت و اشغال |
| `start.sh` واقعاً سرور را بالا می‌آورد | اجراکننده‌ی شکسته |
| `start.cmd`: CRLF، بدون `timeout /t`، بدون `start <url>` | `cmd.exe` شکسته |

نتیجه: **۲۸ بررسی، ۰ ناکام**.

مجموع پس از این دور: `npm test` → exit 0 · **۲۱۰۴ خط ✔، ۰ ناکام**
(روش شمارش همان روش دورهای قبل: خطوط ✔ خروجی؛ ۳۴ خلاصه‌ی «۰ ناکام» + یک
سوئیت بدون خلاصه).
· `typecheck` پاک · `release:check` exit 0.

## چه چیزی روی این سیستم سنجیده نشد (صادقانه)

* **ویندوز نداریم.** `start.cmd` اجرا نشد؛ درستی‌اش از سه راه ایستا تأیید شد
  (CRLF، نبود ساختار شکننده، وجود مسیرهای Node).
* **Tauri CLI و Rust نداریم.** `tauri build` اجرا نشد. شکستِ گزارش‌شده از روی
  همان پیام خطا و با شبیه‌سازی `glob` بازسازی شد، ولی `.msi` واقعی ساخته نشد.
* باز شدن مرورگر روی ویندوز (`rundll32`) اجرا نشد؛ فقط «کشتنِ سرور در اثر
  شکست» بررسی شد.
