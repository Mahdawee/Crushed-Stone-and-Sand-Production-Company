# بازرسی دور ۴۳ — سه شکایت، سه باگ واقعی

## ۱) «ابزار ریست بعد از نصب باز نمی‌شود» ← **باگ اصلی، بازتولید شد**

`scripts/build-desktop.mjs` فقط پوشه‌ی `tools/reset-ui` را داخل بسته کاپی
می‌کرد. ولی خود فایل `tools/reset-ui/server.mjs` این خط را دارد:

```js
import { listenWithFallback, openBrowser } from '../shared/tool-server.mjs';
```

`tools/shared/` **داخل بسته نبود**. بازسازی همین وضعیت:

```
$ node server.mjs --port 4498
Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  '/tmp/stage/tools/shared/tool-server.mjs'
  imported from /tmp/stage/tools/reset-ui/server.mjs
```

یعنی پنجره‌ی cmd باز می‌شد، Node می‌مرد، پنجره **فوراً** بسته می‌شد. مشتری
فقط یک پلک می‌دید. روی کمپیوتر توسعه دیده نمی‌شد چون `tools/shared/`
همان‌جا کنارش هست.

**رفع:** `BUNDLED_SHARED = ['shared']` به فهرست کاپی اضافه شد، و
`stageTools()` حالا **هر `import './…'` و `'../…'` را بعد از کاپی بررسی
می‌کند** — اگر پیدا نشد، ساخت همان‌جا متوقف می‌شود، نه روی لپ‌تاپ مشتری.

اثبات: درخت مستقل نصب ساخته شد، ابزار بالا آمد و `/__tool` جواب داد.

## ۲) «بیلد آخرین اصلاحات را نمی‌سازد» ← **باگ دوم**

```js
const needPack = !fs.existsSync(apiEntry) || (isWin && !fs.existsSync(nodeInBundle));
```

این شرط فقط **وجود** فایل را می‌سنجید. یک بار که ساخته می‌شد، دفعه‌ی بعد
مرحله‌ی بسته‌بندی **رد می‌شد** حتی اگر کد API یا رابط کاربری تازه عوض شده
بود. نصب‌کننده‌ی تازه همان `app.js` و همان `web/` قدیمی را داشت. ما فکر
می‌کردیم اصلاحات را فرستاده‌ایم؛ مشتری نسخه‌ی قبلی می‌گرفت.

**رفع:** حالا **تازگی** سنجیده می‌شود، نه وجود. اگر `apps/api/dist` یا
`apps/web/dist` از بسته‌ی موجود تازه‌تر باشند، دوباره بسته‌بندی می‌شود و
دلیلش را هم می‌گوید:

```
▶ ۲/۳ بسته‌ی API کهنه است — دوباره ساخته می‌شود:
     apps/web/dist تازه‌تر است
```

## ۳) «چک‌های گیت‌هاب قرمز» ← **چک خودش خراب بود**

`test-windows` روی **هر اجرا** در همین مرحله شکست می‌خورد:

```bash
for f in tools/*/start.cmd; do
  if ! grep -q $'\r' "$f"; then ... fail=1; fi
done
```

از دور ۴۰ که این مرحله اضافه شد، **یک بار هم سبز نشد** — در حالی که همان
فایل‌ها روی لینوکس CRLF داشتند (`git ls-files --eol` → `attr/text eol=crlf`،
و در کلون تازه و با هر `core.autocrlf` آزموده شد). یعنی چک، ابزار خرابی
بود که به همه می‌گفت «فایل‌ها خراب‌اند».

این بدترین نوع تست است: سیگنالی که همیشه قرمز است، بعد از مدتی هیچ‌کس
نگاهش نمی‌کند و خطای واقعی هم لای آن گم می‌شود.

**رفع:** `scripts/check-cmd-crlf.mjs` با Node نوشته شد (یک ابزار، روی هر
سیستم، با شماره‌ی خط دقیق). با تبدیل عمدی یک فایل به LF آزموده شد → قرمز شد.

`test-linux` هم در یک اجرا شکست خورد و در اجرای دیگر سبز بود — یعنی
ناپایدار، نه همیشه‌خراب. سه سوئیت پورت ثابت دارند (۴۴۲۳، ۴۴۳۱، ۴۴۳۳) و اگر
سوئیتِ قبلی سرورش را زودتر نبندد، سوئیتِ بعدی «پورت اشغال است» می‌گیرد.
این را در `npm test` محلی هم دیدم و با بستن پروسه‌ی جامانده رفع شد.

**لاگ‌های GitHub Actions از این محیط خوانده نمی‌شوند** (`results-receiver`
و `productionresultssa2.blob.core.windows.net` در دسترس نیستند؛ فقط
`github.com`/`api.github.com` مجاز است). پس برای `test-linux` نتوانستم
پیام دقیق خطا را ببینم. آنچه دارم: نام مرحله (کل تست‌ها)، و این‌که همان
دستور در کلون تازه‌ی محلی سبز است (۲۵۴۲ بررسی).
