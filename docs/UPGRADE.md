# بروزرسانی بدون خراب شدن داده — قاعده‌های ثابت

> این سند برای **آینده** نوشته شده: هر کسی (شامل خود ما در دور بعد) که
> ساختار دیتابیس را عوض می‌کند، باید همین قاعده‌ها را رعایت کند. بدون این
> قاعده‌ها، بروزرسانی روی نصب‌های مشتری می‌تواند داده را نیمه‌کاره یا ناسازگار
> کند — و داده‌ی یک سال کار، جایگزین ندارد.

---

## ۱) دو نسخه‌ی جدا

| چه چیزی | کجا | چه وقت عوض می‌شود |
| --- | --- | --- |
| **نسخه‌ی برنامه** | `package.json` → `version` و `src-tauri/tauri.conf.json` | هر انتشار (۱٫۰٫۱ ← ۱٫۰٫۲) |
| **نسخه‌ی شکل دیتابیس** | `apps/api/src/common/upgrade.ts` → `SHAPE_VERSION` | فقط وقتی جدول/ستون تازه اضافه می‌شود |

نسخه‌ی شکل داخل خود فایل دیتابیس ذخیره می‌شود (`PRAGMA user_version`). چون
داخل فایل است، همراه کاپی/پشتیبان/انتقال به کمپیوتر دیگر می‌رود — یعنی هر
نصب می‌داند ساختارش چند است و چه چیزی کم دارد.

## ۲) قاعده‌ی طلایی: مهاجرت فقط «اضافه» می‌کند

مجاز:
- `CREATE TABLE IF NOT EXISTS …`
- `ALTER TABLE … ADD COLUMN …` (با `DEFAULT` مناسب)
- `CREATE INDEX IF NOT EXISTS …`
- پُرکردن مقدار خالی با `UPDATE` (بدون تغییر معنا)

**ممنوع** (مگر با مهاجرت دومرحله‌ای و تست مهاجرت):
- `DROP COLUMN` / `DROP TABLE`
- تغییر نوع ستون یا `NOT NULL` کردن ستونی که مقدار خالی دارد
- تغییر نام ستون یا جدول
- حذف/تغییر معنا‌ی ردیف‌های موجود (مثلاً بازنویسی شماره‌ی اسناد)

اگر روزی لازم شد ستونی حذف شود، مسیر درست: اول نسخه‌ای که دیگر آن ستون را
**نمی‌خواند** منتشر شود، چند نسخه بعد (بعد از مطمئن شدن از بروزرسانی همه)
در مهاجرت جداگانه حذف شود — نه در همان نسخه‌ای که وابستگی برداشته می‌شود.

## ۳) چه چیزی خودکار انجام می‌شود (و نباید دستی تکرار شود)

هنگام بالا آمدن برنامه، `ensureSchemaAsync()`:

1. جدول‌ها و ایندکس‌های غایب را می‌سازد (`CREATE … IF NOT EXISTS`).
2. اگر مهر ساختار عقب‌تر از `SHAPE_VERSION` باشد:
   - **اول پشتیبان** `backups/pre-upgrade-v<N>-<زمان>.db` (حداکثر ۳۰ فایل
     `pre-upgrade-*` نگه داشته می‌شود).
   - اگر پشتیبان گرفته نشد (جا/دسترسی) ⇒ **مهاجرت انجام نمی‌شود** و برنامه
     با پیام فارسی + راه‌حل بالا نمی‌آید. داده دست‌نخورده می‌ماند.
   - ستون‌های غایب `UPGRADES` اضافه می‌شوند.
   - `quick_check` بعد از مهاجرت؛ اگر ناسالم بود ⇒ برگردانی خودکار از همان
     پشتیبان و پیام صریح.
   - یک خط در `<dataDir>/upgrade-history.log` نوشته می‌شود.
3. اگر مهر ساختار از `SHAPE_VERSION` **جلوتر** باشد (کاپی از نسخه‌ی جدیدتر
   روی برنامه‌ی قدیمی): هیچ نوشتنی انجام نمی‌شود، هشدار در لاگ و در پنل
   «تنظیمات → بروزرسانی و سازگاری داده» نشان داده می‌شود.

## ۴) چک‌لیست انتشار نسخه‌ی جدید

```bash
# ۱) ساختار عوض شد؟  ⇒ SHAPE_VERSION را یک بالا ببر و در جدول بالای upgrade.ts بنویس
# ۲) کل تست‌ها (شامل تست مهاجرت)
npm test                    # باید ۰ ناکام باشد، از جمله test:upgrade
# ۳) ساخت بسته
npm run desktop:build
```

`npm run test:upgrade` یک **نصب قدیمی واقعی** می‌سازد (ساختار ۵، با داده،
بدون ستون‌های تازه) و برنامه‌ی امروز را روی همان فایل بالا می‌آورد؛ بعد
بررسی می‌کند که مشتریان/بل‌ها/مبالغ دست‌نخورده مانده‌اند و پشتیبان پیش از
مهاجرت گرفته شده است. اگر این تست سبز نبود، انتشار نکنید.

## ۵) اگر مشتری گفت «بعد از بروزرسانی چیزی خراب شد»

از کاربر این دو فایل را بگیرید:

```
%APPDATA%\af.farday.roshan\upgrade-history.log
%APPDATA%\af.farday.roshan\api.log
```

`upgrade-history.log` می‌گوید کدام نسخه، از کدام ساختار به کدام ساختار رفت،
پشتیبانش چه نامی داشت و موفق بود یا نه. بازگردانی:

```
Farday Roshan.exe --cli --recovery --list-backups
Farday Roshan.exe --cli --recovery --restore-backup pre-upgrade-v5-....db
```

پشتیبان قبل از بازگردانی بررسی می‌شود (SQLite واقعاً باز و `quick_check`
می‌شود)؛ فایل خراب پذیرفته نمی‌شود و دیتابیس فعلی دست‌نخورده می‌ماند.

## ۶) پشتیبان‌های خودکار (جا و نگه‌داری)

| چه وقت | پیشوند | چرا |
| --- | --- | --- |
| قبل از مهاجرت ساختار | `pre-upgrade-v<N>-` | بروزرسانی برنامه |
| قبل از «صفر کردن» | `pre-reset-` | تحویل آک به مشتری |
| قبل از بازگردانی پشتیبان | `before-restore-` | خودِ عمل بازگردانی |
| پشتیبان دستی (دکمه‌ی برنامه) | `farday-` | خواسته‌ی کاربر |

همه در `<dataDir>/backups/`. پشتیبان‌های دستی تا ۳۰ فایل نگه داشته می‌شوند؛
پشتیبان‌های `pre-upgrade-*` هم مستقل تا ۳۰ فایل (وگرنه هر بروزرسانی یک فایل
تازه می‌گذاشت و پوشه بی‌مرز رشد می‌کرد).
